# Безопасность и приватность

## Что реализовано

В проекте реализованы базовые меры безопасности, достаточные для исследовательского прототипа:

- регистрация и вход пользователя;
- хеширование паролей через Werkzeug;
- bearer-токены на основе `itsdangerous.URLSafeTimedSerializer`;
- срок жизни токена через `AUTH_TOKEN_MAX_AGE_SECONDS`;
- требование `JWT_SECRET` или `SECRET_KEY` в production-режиме;
- роли `patient`, `doctor`, `researcher`, `admin`;
- защита основных медицинских endpoint'ов: `/api/predict`, `/api/commentary`, `/api/report`, `/api/batch-predict`;
- лимиты запросов через `flask-limiter`, если пакет установлен;
- ограничение размера запроса через `MAX_CONTENT_LENGTH = 1 MB`;
- CORS через переменную `FRONTEND_ORIGIN`;
- request ID для трассировки;
- JSON audit log без записи полных лабораторных данных.

## Аутентификация и роли

Пользователь создает учетную запись и получает bearer-токен. Медицинские запросы требуют заголовок `Authorization: Bearer <token>`. Роли нормализуются в `services/database.py`; например, `clinician` соответствует `doctor`, а `scientist` соответствует `researcher`.

Endpoint `/api/batch-predict` дополнительно поддерживает API-key RBAC через `ROLE_API_KEYS`, но теперь также требует обычную bearer-аутентификацию.

## Audit log

Audit log фиксирует технические события: действие, роль, статус, HTTP-код, request ID, IP, путь и дополнительные агрегированные поля. Для `/api/predict` сохраняются только риск, вероятность и время обработки, а не полный набор медицинских показателей. Это снижает риск утечки чувствительных данных через журналы.

## Хранение данных

В прототипе используется SQLite. В таблице анализов сохраняются введенные показатели, SHAP-факторы, вероятность, комментарий и метрики. Это удобно для демонстрации истории и исследовательской панели, но не является полноценной медицинской инфраструктурой хранения.

## Ограничения

Проект не заявляет HIPAA, FDA, CE/MDR или другую регуляторную сертификацию. Также в прототипе не реализованы:

- промышленное управление секретами;
- обязательный TLS на уровне приложения;
- шифрование записей в БД на уровне приложения;
- политика удаления и срока хранения данных;
- согласие пациента и юридический workflow;
- разграничение доступа врача к конкретным пациентам;
- резервное копирование и disaster recovery;
- независимый penetration test и security review;
- мониторинг аномального доступа.

## Что нужно для реального медицинского внедрения

Для реального использования с медицинскими данными нужны внешняя клиническая валидация, юридическая оценка, модель управления рисками, сертификация по применимым нормам, защищенная инфраструктура, контроль доступа на уровне пациентов, шифрование, политика хранения данных и формальный процесс реагирования на инциденты.
