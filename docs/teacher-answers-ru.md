# Ответы на замечания по проекту

Проект формулируется как исследовательский веб-прототип для оценки риска, а не как диагностическая медицинская система. Модель анализирует только ограниченный набор лабораторных показателей ОАК/СОЭ и возвращает вероятность принадлежности к группе повышенного риска. Она не использует КТ, МРТ, ЭУС, гистологию, анамнез, осмотр врача и клиническое решение. Поэтому результат нельзя трактовать как диагноз; он должен использоваться только как вспомогательный сигнал для обсуждения с врачом.

## 1. Почему это не диагноз, а оценка риска

Система не подтверждает рак поджелудочной железы и не назначает лечение. Выход модели состоит из вероятности риска, класса риска, факторов SHAP и пояснительного комментария. Диагноз в реальной практике требует комплексной клинической оценки, инструментальных методов визуализации, лабораторной верификации, а часто и морфологического подтверждения. В интерфейсе, README и PDF-отчетах проект обозначен как исследовательский прототип и инструмент поддержки анализа риска.

## 2. Данные, выборки и значение процента качества

Исходный файл данных: `Набор данных.xlsx`; скрипт подготовки берет первый лист книги. Целевая колонка: `Наличие болезни`, где `да` означает положительный класс, `нет` отрицательный класс. В исходном листе найдено 1254 строки: 1115 отрицательных и 139 положительных записей.

Старые признаки `glucose`, `act`, `bilirubin` не использованы, потому что после удаления пропусков по старой схеме оставалось только 46 полных строк, причем все они относились к положительному классу. На таком наборе нельзя честно обучить бинарную модель. Поэтому выбрана более полная CBC/ESR-схема из 18 признаков: `wbc`, `rbc`, `plt`, `hgb`, `hct`, `mpv`, `pdw`, `neut_abs`, `neut_pct`, `lymph_abs`, `lymph_pct`, `mono_abs`, `mono_pct`, `eos_abs`, `eos_pct`, `baso_abs`, `baso_pct`, `esr`.

После очистки и отбора признаков осталось 1203 пригодные строки: 1115 отрицательных и 88 положительных. Разделение выполнено стратифицированно с `random_state=42`: 70% обучение, 10% валидация, 20% тест. Размеры выборок: обучение 841 строка, валидация 121 строка, тест 241 строка.

Старый процент качества из презентационных материалов больше не используется как основной результат, потому что он не был воспроизводимо привязан к конкретной выборке, порогу и метрике. Текущий воспроизводимый результат берется из `backend/models/user_cbc_rf.metrics.json`: accuracy на отложенной тестовой выборке равен 0.975104 при пороге 0.3, выбранном на валидационной выборке. Это означает долю правильных предсказаний на 241 тестовой записи, а не клиническую точность диагноза.

## 3. Метрики модели кроме accuracy

На тестовой выборке использованы следующие метрики:

- `accuracy`: 0.975104.
- `precision`: 0.875000.
- `recall / sensitivity`: 0.777778.
- `specificity`: 0.991031.
- `f1_score`: 0.823529.
- `mcc`: 0.811813.
- `roc_auc`: 0.974963.
- `pr_auc`: 0.879479.
- `log_loss`: 0.096632.
- `brier_score`: 0.025834.

Матрица ошибок на тесте: TN=221, FP=2, FN=4, TP=14. В задаче с дисбалансом классов accuracy недостаточно, поэтому дополнительно показаны recall, precision, specificity, F1, MCC, ROC-AUC и PR-AUC.

## 4. Что генерирует LLM и как исключаются опасные выводы

LLM не делает предсказание. Сначала backend рассчитывает вероятность риска моделью Random Forest и получает факторы SHAP. После этого LLM получает уже готовый результат: класс риска, вероятность, несколько ведущих факторов и выбранные лабораторные значения. Его задача - сформировать понятный текстовый комментарий для пациента, врача или исследователя.

Инженерные ограничения LLM:

- В prompt явно указано, что это screening aid, а не диагноз.
- LLM не получает права менять вероятность, класс риска или SHAP-факторы; под SHAP-диаграммами объясняется только вклад признаков в уже рассчитанную оценку.
- Ответ должен завершаться напоминанием, что окончательные решения принимает лечащая медицинская команда.
- После генерации добавлен фильтр опасных фраз: утверждения вида "you have pancreatic cancer", "diagnosis: pancreatic cancer", "у вас рак поджелудочной железы", "назначить химиотерапию" блокируются.
- Если LLM недоступна, ответ нечитабелен или содержит опасную формулировку, backend использует детерминированный шаблонный комментарий.

Таким образом LLM отвечает только за объяснение уже рассчитанного результата, а не за медицинское заключение.

## 5. Защита медицинских данных и API

В текущем прототипе реализованы прикладные меры безопасности:

- Регистрация и вход пользователя; пароли хранятся как хеши Werkzeug, а не в открытом виде.
- Основные медицинские endpoint'ы защищены bearer-токеном и ролями: `patient`, `doctor`, `researcher`, `admin`.
- Для запросов включены request ID и JSON-аудит действий без записи PHI в audit log.
- Для API заданы лимиты частоты запросов: например, `/api/predict` ограничен 10 запросами в минуту.
- Ограничен размер входящего запроса через `MAX_CONTENT_LENGTH`.
- CORS настраивается через переменную окружения `FRONTEND_ORIGIN`.
- В production backend требует `JWT_SECRET` или `SECRET_KEY`, чтобы не использовать dev-секрет.

Ограничение прототипа: локальная SQLite-база и файлы отчетов не являются полноценной промышленной инфраструктурой для медицинских данных. Для реальной эксплуатации нужны TLS, секреты вне кода, шифрование диска или БД, политика хранения и удаления данных, резервное копирование, журналирование доступа, согласие пациента и отдельный security review.
